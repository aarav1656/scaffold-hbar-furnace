# Agent instructions

Briefing for coding agents working in this repo (Claude Code loads it through `CLAUDE.md`; Cursor and Codex read it directly).

This is the **Furnace** Scaffold-HBAR template: a buyback-and-burn engine on Hedera. `FurnaceEngine` creates the team's HTS token with itself as treasury and sole supply-key holder, pairs it with WHBAR on SaucerSwap V1 and locks the liquidity. HBAR sent to it is protocol revenue: on its own Hedera Schedule Service schedule the engine buys the token back inside a Chainlink-priced USD daily budget, never above a USD price ceiling, never moving the pool by more than a set price impact, then burns what it bought. Supply is enforced by the network, so every burn is visible in the mirror node's `total_supply`.

## Units: the most common source of bugs here

- **HBAR in the EVM is tinybar (8 decimals).** `msg.value`, `address(this).balance` and the value of `swapExactETHForTokens` are tinybar. At the JSON-RPC layer wallets send 18-decimal weibar, so the frontend uses `parseEther("10")` for 10 HBAR and the contract sees `1_000_000_000`. Measured on testnet: a swap of 200,000,000 spent exactly 2 HBAR.
- USD figures (`dailyBudgetUsd`, `priceCeilingUsd`, `hbarUsd()`, `status().priceUsd`) have 8 decimals. The ceiling and `priceUsd` are USD per **whole** token.
- Token amounts are raw units of the token's own decimals. HTS amounts are `int64`; the engine converts with `SafeCast`, never a bare cast.
- `poolCreationFee()` is tinybar. SaucerSwap prices the pair fee in tinycents ($2.00 = 2e10) and the engine converts it through the exchange rate system contract at 0x168 at call time.
- A V1 pair sorts its two tokens by address. WHBAR (0x3aD2) sorts below any token created recently, so `getReserves()` returns (WHBAR, token); the engine reads `token0()` once in `createPool` and handles both orders (a test suite runs every buyback test again with the order flipped).

## Invariants: do not break these

1. **The owner cannot move HBAR, LP tokens or bought tokens out.** There is no withdraw, sweep or rescue function. HBAR leaves only through the HTS and pair creation fees, the router and the gas of the engine's own schedules. `test_stateChangingSurface_isExactlyTheReviewedList` reads the compiled ABI and fails when a state-changing function is added; update the list only after reviewing the new function.
2. **LP tokens never leave.** `seedLiquidity` mints them to the engine and no function transfers or approves them.
3. **Burns burn only what the swap just delivered.** `buyback` measures the token balance before and after the swap and burns the difference, then asserts the treasury still holds `teamUnclaimed + liquidityUnseeded` (`AllocationBreach` otherwise). Team and liquidity allocations are never burned.
4. **The fuel reserve is never spent on a buyback.** Spendable revenue is `balance - fuelReserve`. Native HBAR is both budget and fuel.
5. **One function sizes the buyback.** `_plan()` is read by `buyback()` and `previewBuyback()`. Caps are checked in a fixed order (funds, budget, ceiling, impact) so a skip names the cap that bound. Spend is the minimum of the four.
6. **The ceiling is a post-trade bound.** `_ceilingHeadroom` solves `(1 + x/R)^2 <= ceiling/price`; the pool fee only lowers the real post-trade price, and every rounding floors, so the pool never ends above the ceiling.
7. **The USD cost of a buyback rounds up**, so rounding never lets a day's spend pass the budget.
8. **`runScheduled` never reverts and books its successor before buying.** It is the only way the automation chain continues. A failed buyback costs one run; a revert would cost the chain. A lost booking sets `runInterval = 0` so automation reads as off and can be restarted.
9. **One `scheduleCall` per transaction.** A second booking in a scheduled execution fails the whole transaction (`NO_SCHEDULING_ALLOWED_AFTER_SCHEDULED_RECURSION`).

## Hedera behaviour the code depends on

| Behaviour | Where it matters |
| --- | --- |
| HTS `createFungibleToken` from a contract takes its fee from the contract's balance; what it does not take stays there | `initialize` sends `msg.value`; measured 11.77 HBAR kept of 20 sent |
| `createPair` associates both tokens inside the call and needs about 6.6M gas; at 4M the inner HTS call returns INSUFFICIENT_GAS and the pair reverts | `createPool` must be sent with an 8M+ gas limit; the live script uses 10M |
| A re-created pair reverts `UniswapV2: PAIR_EXISTS` | `createPool` runs once |
| The engine must be associated with the pair's LP token before `addLiquidityETH` mints to it | `createPool` associates through HIP-719 |
| `price0CumulativeLast` / `price1CumulativeLast` are zero until the first swap | The engine prices from spot reserves and Chainlink, never a TWAP |
| A scheduled call runs with `msg.sender` = the contract that booked it | `runScheduled` uses it as its only access check (`OnlySelf`), and `buyback` accepts `address(this)` |
| `scheduleCall` alone costs about 1.4M gas; a self-rescheduling call under 3M gas runs once and silently fails to book its successor | `MIN_SCHEDULED_GAS = 3_000_000`; deploy uses 4M |
| Expiry more than 62 days out is refused | `MAX_INTERVAL = 60 days` |
| A busy second refuses new schedules (`SCHEDULE_EXPIRY_IS_BUSY`) | `_secondWithCapacity` probes +1, +2, +4, +8, +16 s |
| The payer must hold the full gas reservation (`scheduledGas` x gas price), not just what a run burns | `fuelReserve` must stay well above 4M gas at about 88 tinybar per gas (3.5 HBAR) plus the cost of the runs to come |
| HTS refuses an allowance above a finite token's max supply | `seedLiquidity` approves exactly the liquidity allocation |
| An account must be associated with an HTS token before it can receive it | The engine is its own token's treasury, so already associated; `claimTeamAllocation` needs its recipient associated first |
| Hedera has no public mempool | A scheduled buy has a known time, which is why price impact and the ceiling bound every run |
| `eth_getLogs` on Hashio is range-limited | The UI reads events from the mirror node `/contracts/{id}/results/logs` |

## Common changes

- **Change the policy for a deploy:** `DAILY_BUDGET_USD`, `MAX_IMPACT_BPS`, `PRICE_CEILING_USD`, `SLIPPAGE_BPS`, `FUEL_RESERVE_HBAR`, `MIN_SPEND_HBAR_E8` in the environment; the owner can change budget, impact, ceiling and slippage later with the `set*` functions (bounded, with events).
- **Mainnet:** swap the router and Chainlink addresses in `Deploy.s.sol` (SaucerSwap docs, Chainlink feed directory) and remove the chain-id gate.
- **New contract behaviour:** add the test first in the matching `test/Furnace*.t.sol`, then change the contract. Mocks are in `test/mocks/`; extend them rather than calling a live network from unit tests.
- **Mutation check before trusting a guard:** break it, run `forge test`, confirm red, restore, confirm green.

## Frontend conventions

- Scaffold hooks: `useScaffoldReadContract`, `useScaffoldWriteContract`, `useScaffoldEventHistory`, `useDeployedContractInfo`, `useTransactor` (in `hooks/scaffold-hbar`).
- `~~` import alias, `"use client"` on pages that use hooks, DaisyUI classes, `type` over `interface`.
- Every number on screen comes from the chain or the mirror node. No hard-coded prices or balances. `status()` returns the whole dashboard in one call and never reverts on a stale oracle.

## Before you call something done

`yarn foundry:test`, `yarn lint`, `forge fmt --check`, `forge lint`, `yarn next:check-types`, `yarn next:build` all pass. For contract changes, also run `yarn foundry:live` and check the HashScan links it prints. A transaction hash proves the network accepted a call; the engine's state afterwards (`totalBurned()`, the mirror node's `total_supply`, `nextRunAt()`) proves it did what you meant. Never verify against an empty pool: seed it first.
