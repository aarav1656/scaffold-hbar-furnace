# Agent instructions

Briefing for coding agents working in this repo (Claude Code loads it through `CLAUDE.md`; Cursor and Codex read it directly).

This is the **Furnace** Scaffold-HBAR template: a buyback-and-burn engine on Hedera. `FurnaceEngine` creates the team's HTS token with itself as treasury and sole supply-key holder, pairs it with WHBAR on SaucerSwap V1 and locks the liquidity. HBAR sent to it is protocol revenue: on its own Hedera Schedule Service schedule the engine buys the token back inside a Chainlink-priced USD daily budget, in lots of bounded size with a minimum gap between buys, never above a USD price ceiling, never moving the pool by more than a set price impact and never while the pool's spot price sits above its own time-weighted average, then burns what it bought. Supply is enforced by the network, so every burn is visible in the mirror node's `total_supply`.

## Units: the most common source of bugs here

- **HBAR in the EVM is tinybar (8 decimals).** `msg.value`, `address(this).balance`, `tx.gasprice` and the value of `swapExactETHForTokens` are tinybar. At the JSON-RPC layer wallets send 18-decimal weibar (1 tinybar = `1e10` weibar), so the frontend uses `parseEther("10")` for 10 HBAR and the contract sees `1_000_000_000`. Measured on testnet: a swap of 200,000,000 spent exactly 2 HBAR, and a 35 HBAR transfer reads `35e18` over JSON-RPC and `3500000000` on the mirror node.
- USD figures (`dailyBudgetUsd`, `priceCeilingUsd`, `hbarUsd()`, `status().priceUsd`) have 8 decimals. The ceiling and `priceUsd` are USD per **whole** token.
- Token amounts are raw units of the token's own decimals (8 on the canonical FURN). HTS amounts are `int64`; the engine converts with `SafeCast`, never a bare cast.
- `poolCreationFee()` is tinybar. SaucerSwap prices the pair fee in tinycents ($2.00 = 2e10) and the engine converts it through the exchange rate system contract at 0x168 at call time.
- The pair's `price0CumulativeLast` / `price1CumulativeLast` are UQ112x112 prices times seconds. The engine tracks the cumulative of HBAR per token (`price0` when the token is `token0`, else `price1`), so `twap()` and `status().twapPriceHbar` come out in tinybar per whole token like `priceHbar`. Only differences of two readings mean anything, and they wrap by design.
- A V1 pair sorts its two tokens by address. WHBAR (0x3aD2) sorts below any token created recently, so `getReserves()` returns (WHBAR, token); the engine reads `token0()` once in `createPool` and handles both orders (a test suite runs every buyback test again with the order flipped).
- `router.whbar()` is the WHBAR HTS token (0x3aD2) and the one swap paths use. `router.WHBAR()` is the wrapper contract (0x3aD1).

## Invariants: do not break these

1. **The owner cannot move HBAR, LP tokens or bought tokens out.** There is no withdraw, sweep or rescue function. HBAR leaves only through the HTS and pair creation fees, the router and the gas of the engine's own schedules. `test_stateChangingSurface_isExactlyTheReviewedList` reads the compiled ABI and fails when a state-changing function is added; update the list only after reviewing the new function.
2. **LP tokens never move.** `seedLiquidity` mints them to the engine and no function transfers or approves them.
3. **Burn only bought tokens.** `buyback` measures the token balance before and after the swap and burns the difference, then asserts the treasury still holds `teamUnclaimed + liquidityUnseeded` (`AllocationBreach` otherwise). Team and liquidity allocations are never burned.
4. **The fuel reserve is never spent on a buyback.** Spendable revenue is `balance - fuelReserve`. Native HBAR is both budget and fuel.
5. **One function sizes the buyback.** `_plan()` is read by `buyback()` and `previewBuyback()`. The minimum gap since the last spend is checked first and needs no oracle (`TooSoon`). Caps are then checked in a fixed order (funds, budget, ceiling, impact, lot) so a skip names the cap that bound, and spend is the minimum of the five. The average-price bound comes last and allows or refuses the buy without sizing it.
6. **The ceiling is a post-trade bound.** `_ceilingHeadroom` solves `(1 + x/R)^2 <= ceiling/price`; the pool fee only lowers the real post-trade price, and every rounding floors, so the pool never ends above the ceiling.
7. **The USD cost of a buyback rounds up**, so rounding never lets a day's spend pass the budget.
8. **Book first, never revert.** `runScheduled` books its successor before buying and never reverts. It is the only way the automation chain continues. A failed buyback costs one run; a revert would cost the chain. A lost booking sets `runInterval = 0` so automation reads as off and can be restarted.
9. **The pool is never bought into above its own average.** The engine keeps a snapshot of the pair's cumulative price (`twapCumulative`, `twapAt`). A buy is refused (`TwapDeviation`) when spot sits more than `maxTwapDeviationBps` above the average since that snapshot, and refused as `NoTwap` or `TwapWindow` when there is no snapshot or it is under `MIN_TWAP_WINDOW` (15 minutes) old; spot is never trusted in place of an average. `buyback()` moves the snapshot on every owner or engine run that gets as far as judging the price (a skip names the reason, a run inside the gap leaves it alone), `seedLiquidity` takes the first one, and a run younger than the minimum window never restarts the clock. `_plan()` only reads it. The check is upward only: buying below the average never hurts the engine. The swap's `minOut` is the larger of the router quote less slippage and `_averagePriceFloor`, which comes from the average price, the allowed deviation, the impact cap and a fee allowance, so a router that quotes and fills a bad price still fails it.
10. **One booking per execution.** A second `scheduleCall` in a scheduled execution fails the whole transaction (`NO_SCHEDULING_ALLOWED_AFTER_SCHEDULED_RECURSION`). `runScheduled` calls `_bookNext` once and nothing under `buyback()` books.

11. **Anyone may trigger a buy only through the gap, and only to spend.** Once `minGapSeconds` is set, `buyback()` is open to everyone, but a call from anyone but the owner or the engine that would not spend reverts `BuybackRefused` and changes nothing, so an outsider can neither fill the logs with skips nor move the price snapshot. With no gap only the owner or the engine may call it. `rearm()` is permissionless but books only when automation is on and the pending schedule is missing or more than `REARM_GRACE` overdue (`ScheduleLive` otherwise), so it cannot start a second chain. `depositRevenue(bytes32)` only adds HBAR to the engine and emits `RevenueTagged`; it sends nothing out.

## Hedera behaviour the code depends on

| Behaviour | Constant or measurement | Where it matters |
| --- | --- | --- |
| HTS `createFungibleToken` from a contract takes its fee from the contract's balance; what it does not take stays there | 20 HBAR sent, about 11.8 HBAR kept by HTS | `initialize` sends `msg.value` |
| `createPair` associates both tokens inside the call | needs about 6.6M gas (6,622,028 measured); at 4M the inner HTS call returns INSUFFICIENT_GAS ("Safe multiple associations failed!") and the pair reverts | `createPool` must be sent with an 8M+ gas limit; the live script uses 10M |
| The pair fee is priced in tinycents | `pairCreateFee()` = 20000000000 ($2.00); 0x168 `tinycentsToTinybars` converts it (1,995,165,050 tinybar at creation) | `poolCreationFee()`, `createPool` |
| A re-created pair reverts `UniswapV2: PAIR_EXISTS` | n/a | `createPool` runs once |
| The engine must be associated with the pair's LP token before `addLiquidityETH` mints to it | HIP-719 `associate()` returns 22, or 194 when already associated | `createPool` associates through `_associate` |
| `price0CumulativeLast` / `price1CumulativeLast` are live on SaucerSwap V1 pairs and `getReserves()` returns the pair's last-update second | v1 pair `0x2989...Cf05`: `price1CumulativeLast` 4.05e34 at reserves 3.4e9 / 2.94e13, 67,000 s of accumulation | `twap()` extends the stored cumulative to now with the current reserves, as UniswapV2OracleLibrary does |
| A scheduled call runs with `msg.sender` = the contract that booked it | n/a | `runScheduled` uses it as its only access check (`OnlySelf`), and `buyback` accepts `address(this)` |
| A self-rescheduling call under 3M gas runs once and silently fails to book its successor | `scheduleCall` alone costs about 1.4M gas; `MIN_SCHEDULED_GAS = 3_000_000`; deploy uses 4,000,000 | The constructor reverts `BadConfig` below the floor |
| One schedule per scheduled execution | exactly one SCHEDULECREATE child per run | `runScheduled` books once, before buying |
| Expiry more than 62 days out is refused | `hasScheduleCapacity` is true at 62 days and false at 63; `MAX_INTERVAL = 60 days` | `startAutomation` reverts `BadInterval` outside 60 s to 60 days |
| A busy second refuses new schedules (`SCHEDULE_EXPIRY_IS_BUSY`) | `_secondWithCapacity` probes +1, +2, +4, +8, +16 s | `startAutomation`, `runScheduled` |
| The payer must hold the full gas reservation, not just what a run burns | 4,000,000 gas x 88 tinybar = 3.52 HBAR reserved; a run is charged about 1.40 to 1.42 HBAR | Keep `fuelReserve` well above the reservation plus the runs to come |
| A scheduled run is billed to the engine's balance | The network fee (141,794,436 tinybar on the first run) is charged on top of the swap value | Revenue funds buys and fees together |
| HTS refuses an allowance above a finite token's max supply | `approve` above `max_supply` returns AMOUNT_EXCEEDS_TOKEN_MAX_SUPPLY | `seedLiquidity` approves exactly the liquidity allocation |
| HTS refuses to burn more than the treasury holds | INSUFFICIENT_TOKEN_BALANCE | The engine burns only what the swap delivered |
| An account must be associated with an HTS token before it can receive it | n/a | The engine is its own token's treasury, so already associated; `claimTeamAllocation` needs its recipient associated first |
| Hedera has no public mempool | n/a | A scheduled buy has a known time, which is why price impact and the ceiling bound every run |
| Scheduled executions appear under mirror `/transactions` (`scheduled: true`) and `/contracts/{id}/results/logs`, not under `/contracts/{id}/results` | n/a | Evidence and UI reads use those two endpoints |
| `eth_getLogs` on Hashio is limited to a 7 day span | 604,800 seconds | The UI reads events from the mirror node `/contracts/{id}/results/logs` |
| Chainlink HBAR/USD has an 8 decimal answer and a 24 hour heartbeat | `maxOracleAge = 1 days + 1 hours` | `hbarUsd()` reverts `StaleOracle` past it |

## Common changes

- **Change the policy for a deploy:** `DAILY_BUDGET_USD`, `MAX_IMPACT_BPS`, `PRICE_CEILING_USD`, `SLIPPAGE_BPS`, `MAX_LOT_USD`, `MIN_GAP_SECONDS`, `MAX_TWAP_DEV_BPS`, `FUEL_RESERVE_HBAR`, `MIN_SPEND_HBAR_E8` in the environment; the owner can change budget, impact, ceiling, slippage, lot, gap and price bound later with the `set*` functions (bounded, with events).
- **Mainnet:** swap the router and Chainlink addresses in `Deploy.s.sol` (SaucerSwap docs, Chainlink feed directory) and remove the chain-id gate.
- **New contract behaviour:** add the test first in the matching `test/Furnace*.t.sol`, then change the contract. Mocks are in `test/mocks/`; extend them rather than calling a live network from unit tests.
- **Mutation check before trusting a guard:** break it, run `forge test`, confirm red, restore, confirm green. The 51 that already exist are listed in `docs/architecture.md`.

## Frontend conventions

- Scaffold hooks: `useScaffoldReadContract`, `useScaffoldWriteContract`, `useScaffoldEventHistory`, `useDeployedContractInfo`, `useTransactor` (in `hooks/scaffold-hbar`).
- `~~` import alias, `"use client"` on pages that use hooks, DaisyUI classes, `type` over `interface`.
- Every number on screen comes from the chain or the mirror node. No hard-coded prices or balances. `status()` returns the whole dashboard in one call and never reverts on a stale oracle.

## Before you call something done

`yarn foundry:test`, `yarn lint`, `forge fmt --check`, `forge lint`, `yarn next:check-types`, `yarn next:build` all pass. For contract changes, also run `yarn foundry:live` and check the HashScan links it prints. A transaction hash proves the network accepted a call; the engine's state afterwards (`totalBurned()`, the mirror node's `total_supply`, `nextRunAt()`) proves it did what you meant. Never verify against an empty pool: seed it first.
